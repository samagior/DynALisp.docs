Program Description

Finds out why DynALisp, or AutoCAD with it, does not work as it should. It reads how DynALisp is installed and started, the AutoCAD running and what else it loads, the settings and files of DynALisp, its reactors and the current drawing, and writes what it finds in a text report that opens in your text editor. The problems found are marked [!] and listed again at the top of the report.

Dyl-Diagnostics (the Diagnostics button of the Troubleshooting panel) writes the full report, with your settings and files, and offers to send it to the developer of DynALisp in a GitHub issue. Each part of the report is also a command of its own, to check one thing quickly.

How It Works

Each part of the report checks one thing:

  • DynALisp: the version installed and the latest release (when Dyl-Info checked it), a git clone (its branch and commit) or the setup, the folder of DynALisp, another copy of DynALisp installed, the DynALisp menu, the settings waiting to be imported and your files. Then the startup of the drawing: its time, the commands and aliases defined, its warnings, the Remote and Reactor files that failed to load and the slowest ones, and the Lisp files of each module.
  • AutoCAD: the product and its version, Windows, the profiles, the system variables that change how programs load and run (SECURELOAD, NOMUTT, FILEDIA...), the support file search path (missing or repeated folders), the trusted locations, acad.lsp, acaddoc.lsp and acad.pgp, the ARX and .NET applications loaded, the menus loaded, the application bundles installed and the AutoCAD Startup Suite (APPLOAD).
  • Conflicts: reads the Lisp files of the other programs AutoCAD loads (acad.lsp, acaddoc.lsp, the AutoCAD Startup Suite, the other application bundles and the support folders outside AutoCAD itself, 300 files at most). A file that defines S::STARTUP with defun (the DynALisp startup may not run), or a command named as a DynALisp command or alias, is a problem; a file that undefines AutoCAD commands or makes reactors is noted. Then the aliases of acad.pgp named as a DynALisp command turned on or an alias defined (one of them hides the other: rename the DynALisp one), the DynALisp aliases not defined because their name is taken, and the reactors of other programs in the drawing.
  • Startup Suite: the commands turned on per module, the files of the Startup Suite missing, the commands turned on but not defined, a command in two files, the main commands without a docs page, and the aliases of a command that is neither in the Startup Suite nor a custom preset (left over from a command removed or renamed: remove them in Dyl-Suite).
  • Settings: every Dynalisp* setting, your files (the User folder, those whose default is newer after an update), and every data file DynALisp reads (CSV): a file that cannot be read, the rows that do not have the fields of their header, and the time to read them all.
  • Reactors: the reactor settings, each reactor turned on has its reactor in the drawing (once), a count of commands stuck or objects piling up, and every reactor of the drawing.
  • Drawing: the file, its units and scales, the active phase and draw order preset, the objects and draw order entries of each space, the layers, the blocks and xrefs (not found or not loaded), the kinds of objects (proxy objects noted), the revisions of its project (its files and the title blocks of the layouts that have revisions, see Revisions) and the time to regenerate it.

A part run alone is written to %TEMP%\DynALisp Diagnostics\<part>.txt and opens in your text editor.

Sending A Report

Dyl-Diagnostics writes every part into a DynALisp Report <date> folder of %TEMP%, with:

  • Report.txt: the report, which opens in your text editor;
  • DynALisp-Settings.txt: your DynALisp settings, as Export settings of Dyl-UserFiles writes them;
  • User: your copies of the data files (presets, aliases, layer keys...).

The folder is zipped next to it. The question Send it to the DynALisp developer in a GitHub issue? then opens, on Open issue, a new issue of the DynALisp releases repository in your browser, its title and summary filled in, and the folder of the zip with the zip selected: describe what happened, drag the zip into the issue, then Submit new issue. Close keeps the report where it is.

A GitHub issue is public: read the report before you send it. The report and the settings file never hold your profile folder, your user name or your computer name: they are replaced by %USERPROFILE%, %USERNAME% and %COMPUTERNAME%. The files of the User folder are sent as they are. The drawing itself is never sent, only what the report says of it.

Finding What Slows AutoCAD

Pst-DiagnosticsReactorEvents (DIAG-EVENTS) counts the events the drawing sends to the reactors: run it, work the slow way for about 20 seconds (zoom, pan, draw), then run it again. The report lists each event (an object added or changed, a command started, a system variable changed) and its count. The DynALisp reactors run only on these events: when none is counted during a slow zoom or pan, the reactors are not what slows it. It needs the DynALisp reactors on (Dyl-Settings).

The Drawing part times a regeneration of the drawing: run DIAG-DWG, change one thing (the draw order table deleted with DO-RESET, the reactors turned off and the drawing opened again...), run it again and compare.

Known Limitations

  • The compiled programs of other applications (.fas, .vlx, .dll) cannot be read: only their name is listed, not the commands they define.
  • The startup records (its time, warnings and load errors) are those of the drawing the report is made in; Dyl-Reload records them again.
  • The kinds of objects are counted up to 100 000 objects; above, only their total is given.
  • Sending the report needs a GitHub account; without one, send the zip by email.
