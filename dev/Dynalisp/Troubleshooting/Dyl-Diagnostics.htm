Diagnostics

The developer docs of Diagnostics: its files and how its code works. What it does and how to use it are in its User Guide page.

Source FilesModules\Dynalisp\Apps\Troubleshooting\Dyl-Diagnostics.lsp (the report, its sections and the commands), Modules\Dynalisp\Reactor\Dyl-Diagnostics.lsp (the event counter, loaded only while the DynALisp reactors are on)
DataReads what DynALisp keeps of its startup (*dyl:startms*, *dyl:startwarn*, *dyl:startnote*, the time of each step *dyl:steptimes*, *dyl:loaderrs*, *dyl:loadtimes*, and whether the library modules were loaded in the drawing, *dyl:libsloaded*, *dyl:libtimes*), the Dynalisp* settings, the data files and the drawing. Writes %TEMP%\DynALisp Diagnostics\<section>.txt and %TEMP%\DynALisp Report <date> with its zip

The Report

Every check adds lines to the report through a few functions, never with princ (the Diagnostics convention):

FunctionLine
(dg:kv key value) key: value (any value, written by dg:str)
(dg:sub title), (dg:item text)a sub-heading -- title, an indented line
(dg:note text) [i] text: worth knowing
(dg:bad text) [!] text: a problem, also added to dg:probs with the name of its section, for the list at the top

The lines go to dg:out, last first. (dg:try f) runs a check in a vl-catch-all-apply: a check that stops is reported as a problem (check dg:x stopped: ...) and the next ones run.

The Sections

dg:sections lists them in order, (name function): dg:s-dynalisp, dg:s-autocad, dg:s-conflicts, dg:s-suite, dg:s-settings, dg:s-reactors, dg:s-interface, dg:s-drawing. Each one runs its checks with dg:try (dg:dyl-install, dg:dyl-startup, dg:acad-paths, dg:cf-files, dg:dwg-revisions...). What each section checks:

How It Works

Each part of the report checks one thing:

  • DynALisp: the version installed and the latest release (when Dyl-Info checked it), a git clone (its branch and commit) or the setup, the folder of DynALisp, another copy of DynALisp installed, What's New (CHANGELOG.md missing, no section for the version installed, no copy in the language of DynALisp: see Info), an AutoCAD older than 2025 (DynALisp 2.0 does not run in it: 1.x does), which build of the plugins AutoCAD loads (dg:net10-p: .NET 10 of Resources\Net10 in AutoCAD 2027 and later, .NET 8 in 2025 and 2026), the plugins not loaded (the core, the ribbon, the windows, the simulation), each named by its path (dg:dll), the data files the core keeps for the session and the time it spent reading them (Dyl:DataInfo, see Core), the steps of the last opening of the Manager in the drawing, the slowest first (*dyl:mgrtimes*, see Manager), the DynALisp menu, the settings waiting to be imported and your files. Then the startup of the drawing: its time, the commands and aliases defined, its warnings, the Remote and Reactor files that failed to load and the slowest ones, and the Lisp files of each module. When Dyl-Assistant or Dyl-TextFix is turned on (dg:dyl-assistant, through Dyl:ClaudeInfo): DynALisp.Assistant.dll loaded, the path and version of Claude Code, whether it is signed in and how, and a note when ANTHROPIC_API_KEY is set.
  • AutoCAD: the product and its version, Windows, the profiles, the system variables that change how programs load and run (SECURELOAD, NOMUTT, FILEDIA...), the support file search path (missing or repeated folders), the trusted locations, acad.lsp, acaddoc.lsp and acad.pgp, the ARX and .NET applications loaded, the menus loaded, the application bundles installed and the AutoCAD Startup Suite (APPLOAD).
  • Conflicts: reads the Lisp files of the other programs AutoCAD loads (acad.lsp, acaddoc.lsp, the AutoCAD Startup Suite, the other application bundles and the support folders outside AutoCAD itself, 300 files at most). A file that defines S::STARTUP with defun (the DynALisp startup may not run), or a command named as a DynALisp command or alias, is a problem; a file that undefines AutoCAD commands or makes reactors is noted. Then the aliases of acad.pgp named as a DynALisp command turned on or an alias defined (one of them hides the other: rename the DynALisp one), the DynALisp aliases not defined because their name is taken, the reactors of other programs in the drawing, and, while Display is on in Dyl-Settings (dg:cf-display), a Theme that the active system variable profile sets otherwise with COLORTHEME (a problem: each startup sets it twice) a display color chosen that another program has changed since (noted), what the ribbon plugin does with the colours of the ribbon and the palettes when Ribbon or Palettes is DynALisp, and with the file tabs when File tabs is set (a problem when the plugin is not loaded or finds nothing to change).
  • Startup Suite: the commands turned on per module, the files of the Startup Suite missing, the commands turned on but not defined, a command in two files, the main commands without a docs page, and the aliases of a command that is neither in the Startup Suite nor a custom preset (left over from a command removed or renamed: remove them in Dyl-Suite).
  • Settings: every Dynalisp* setting, your files (the User folder, those whose default is newer after an update), and every data file DynALisp reads (CSV): a file that cannot be read, the rows that do not have the fields of their header, and the time to read them all; then the assembly presets of Quick Draw (dg:set-asm): how many, the default assemblies of the building code (read from the file as shipped, so a user copy that does not have them yet still counts them), and the Quick Draw presets whose assembly no longer exists; then the materials (dg:set-mat): a materials file of DynALisp 1.1 or older not split yet (never split by the report, which changes no file), how many materials and hatch presets, the materials whose hatch preset no longer exists, the materials in a group that is not one of the groups of the materials (MaterialGroups.csv, a note), and a User copy of the HatchPresets.csv of DynALisp 1.0, which is not read.
  • Reactors: the reactor settings, each reactor turned on has its reactor in the drawing (once), a count of commands stuck or objects piling up, and every reactor of the drawing.
  • Interface (Pst-DiagnosticsInterface): the Display settings and COLORTHEME, then the diagnostics of DynALisp.Ribbon.dll gathered: the status of the ribbon, the palettes and the file tabs ((Dyl:RibbonSkin), "Palettes", (Dyl:RibbonFileTabs)), the native palettes ("Native") and the web pages ("Web"), and the reports the plugin writes to %TEMP%, read back by dg:if-file (800 lines at most): what was done when since it loaded ("Timeline"), what still shows a blue-grey of AutoCAD ("Hosted") and, only where the plugin found them (the status of the palettes names CAcColorTheme with its colours: AutoCAD 2027), the colour themes of AutoCAD in C++ ("Hosted" "Colors", read only). "Push", which changes the themes, is never run. The problems of the interface stay in Conflicts (dg:cf-display). Then the Start page (dg:startpage, DynalispStartPage and STARTMODE with the settings): the lines of (Dyl:StartPage), a problem when it is on and not shown (its plugin not loaded, STARTMODE 0, the Start tab not found), and while it is on the file of (Dyl:StartPage "Tree") (see Start Page). Then Active time (dg:activity, DynalispActivity with the settings): the lines of (Dyl:Activity), no path in them, a problem when it is on without its plugin or could not write its time, a note when the Start page is off.
  • Drawing: the file, its units and scales, the active phase and draw order preset, the objects and draw order entries of each space, the layers, the blocks and xrefs (not found or not loaded), the kinds of objects (proxy objects noted), the revisions of its project (its files and the title blocks of the layouts that have revisions, see Revisions), the objects that carry a material (dg:dwg-materials: how many, how many closed outlines, how many materials, a problem for each material used that no longer exists; counts only, see Assign Material), the simulation zones and climate zones (dg:dwg-simulation: the climates of Climates.csv, a note for those without a temperature, those with their months and a note for those with some months and not all, a problem for a climate zone of a climate the file no longer has, see Simulation) and the time to regenerate it.

A part run alone is written to %TEMP%\DynALisp Diagnostics\<part>.txt and opens in your text editor.

Writing And Sending

  1. (dg:report names) clears dg:out and dg:probs, runs the sections named (setting dg:sect for dg:bad), and returns the lines: a heading with the date, the version and the product, the count and list of the problems, then the sections.
  2. (dg:write path lines) writes them in UTF-8 when AutoCAD can, each line through dg:anon, which replaces USERPROFILE (and the profile part of TEMP), USERNAME and COMPUTERNAME by their variable names: the report goes to a public issue.
  3. A section alone (dg:one, the Pst-Diagnostics* children) is written to %TEMP%\DynALisp Diagnostics\<name>.txt and opened with dg:open (ShellExecute of Shell.Application: the text editor of Windows).
  4. The full report (dg:full, c:Dyl-Diagnostics) goes to a DynALisp Report <date> folder: Report.txt, DynALisp-Settings.txt (dg:settingsfile: every Dynalisp* setting as Name=Value, the format of Export settings) and the User folder (Dyl:SetsCopy), its User\Start removed (Dyl:UserRmDir: the active time and the pins of the Start page are never in a report). dg:zip zips it with PowerShell's Compress-Archive, run hidden by dg:run (WScript.Shell, waiting for it).
  5. dg:full-ask opens it and Dyl:Ask offers to send it. dg:issue builds the address of a new issue of *dyl:gitrepo* (DynALisp.bundle): its title, and a body with the summary and the problems, cut at about 3500 characters (the rest is in the zip), percent-encoded in UTF-8 by dg:url. The issue opens in the browser and Explorer selects the zip. DynALisp never sends anything by itself. Run by Report a problem of the Start page, *dg:forissue* is set: dg:full clears it, asks nothing and gives the report and its zip to (Dyl:StartPageIssue report zip) of the plugin (nil nil when the report could not be written), which opens the issue with what the user typed.

Reactor Events

Pst-DiagnosticsReactorEvents (dg:events) runs twice. The first run starts the counting reactors of Reactor\Dyl-Diagnostics.lsp (Reactor>>Dyl:DiagEventsStart), made for a moment and removed when it runs again, so they need no setting (Reactors convention). The second run stops them (Reactor>>Dyl:DiagEventsStop returns the time and the count of each event) and writes the report. With the reactors off, there is no event to count: it says so. The same two runs time the .NET plugins, whose work on the idle of AutoCAD and on timers no reactor sees: the first run calls (Dyl:RibbonWork "Start") and (Dyl:SheetSets "Work" "Start") (*dg:worktest* is then T in the drawing), the second (Dyl:RibbonWork) and (Dyl:SheetSets "Work"), whose lines end the report. Installer\Ribbon\Plugin\Work.cs times each step of the ribbon plugin (Work.Time, a Stopwatch read; Work.Count for what is only counted: an Idle event, every window repainted), and during the test a thread of its own puts a call on the dispatcher of AutoCAD every 25 ms: a call that waits 100 ms or more is a stall (AutoCAD not reading its messages), listed with the steps of 5 ms or more that ran in it. Another thread reads the cursor of Windows every 5 ms (GetCursorInfo): each change is counted (by the system cursors it goes from and to), with the time between two changes (a rhythm points to a timer) and the steps that ended in the 40 ms before it. To find which part of the ribbon plugin slows AutoCAD without starting it again, (Dyl:RibbonWork "Off" "<part>") turns a part off until AutoCAD closes and (Dyl:RibbonWork "On" "<part>") turns it back on: idle (the Idle event no longer handled), the parts of the colours of the interface, whose colours go back to those of AutoCAD (themes, native, cpp, hosted, web, or colours for the five), filetabs, ribbon (the drop-downs and the translation), timers (the timers of the colours stopped), commands, or all; (Dyl:RibbonWork "Parts") lists those off. The parts off are kept in DynalispRibbonOff (a setting of this computer, never saved with the settings), so a slowness that comes and goes can be watched for a whole session; the Interface section of the report says when parts are off.

Record

Pst-DiagnosticsRecord (dg:record) is a toggle on (Dyl:RibbonRecord) of Installer\Ribbon\Plugin\Recorder.cs: when it returns a file a recording runs, so (Dyl:RibbonRecord "Stop") ends it and dg:open opens the file; otherwise (Dyl:RibbonRecord "Start") starts one and the command line says it is on and how to end it. Without the ribbon plugin, it says nothing can be recorded. Recorder.Begin writes a header (AutoCAD, the drawings open, Display, Interface, File tabs and Work.PartsOff), subscribes to the drawings opened, made current and closed and to the commands of every drawing, and starts two threads: one puts a call on the dispatcher every 50 ms (a wait of 100 ms or more is a stall, written at once from 300 ms with the command running and the steps of 5 ms or more in it), one counts the changes of the Windows cursor (GetCursorInfo, 5 ms). Work.Add gives every step of the plugin to Recorder.Step while it records (on the thread of AutoCAD only), which keeps the totals of the minute and of the whole recording and the steps of the last 15 s. A DispatcherTimer of 1 s appends the pending lines to the file (File.AppendAllLines, so nothing is lost if AutoCAD stops) and writes the summary of each minute. The badge is a WPF window owned by the main window (XAML parsed in the code, top right of AutoCAD, dragged with DragMove), in English or French after DynalispLanguage; its Bug now calls Recorder.Mark (the steps of the last 15 s), Stop Recorder.Stop(true) (the summary of the recording, the file opened). BeginQuit stops it. The time without an Idle of AutoCAD is only in the summary: AutoCAD sends none while nothing happens. The Interface section of the report notes a recording running.

Witness Files

Pst-DiagnosticsWitness (dg:witness) loads Installer\Core\Tests\Witness\Witness.lsp of the git clone (*dyl:repo), which runs at once: the Lisp code that DynALisp.Core replaces run on the cases of Witness\In, zipped in %TEMP% (see its header and Core). A setup has no Installer folder: the command then says so.

Adding A Check

A tool that adds a startup step, a reactor, a data file, a setting or a way to conflict with other programs adds its check in the same change, in the section it belongs to: a function dg:<section>-<what> using dg:kv, dg:bad and dg:note, called with dg:try from its dg:s-* function. A function it calls from another file is checked first, (if Remote>>Dyl:X ...).

Known Limitations

  • dg:events builds its folder and file with "\DynALisp Diagnostics" and "\Reactor Events.txt", with one backslash: AutoLISP reads a backslash as the start of an escape, so the separator is likely lost and the report written beside the temporary folder (...\TempDynALisp Diagnostics) instead of in it. They should be "\\DynALisp Diagnostics" and "\\Reactor Events.txt", as in dg:one.
  • The other programs are read as text: a compiled .fas, .vlx or .dll gives only its name. The conflict check reads 300 files at most.
  • The kinds of objects are counted up to 100 000 objects.
