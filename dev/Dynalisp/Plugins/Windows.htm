Windows

The developer docs of the windows of DynALisp: the plugin that shows them, the window files, and how a DCL window is moved to it. What the user sees is in its User Guide page.

Why WPF

A DCL window cannot be resized, has no real list or tab, looks like Windows 95 and can only be pictured by running AutoCAD. A WPF window looks like the rest of Windows, and its picture is drawn from its file, without AutoCAD, as the pictures of the ribbon are. DynALisp already needs .NET for the ribbon drop-downs and the clean startup; AutoCAD LT and AutoCAD for Mac were never supported (no full AutoLISP, no ActiveX). The cost: AutoCAD 2015 is now the oldest version (the first one the .NET Framework plugin loads in), and each window is rewritten once.

How It Works

  1. The Lisp calls (Dyl:WinShow file vals): file a .xaml of Modules\Dynalisp\Res (or a full path), vals the values of its keys, as set_tile takes them. Dyl:WinDocs reads the file and its sub-windows for their docs pages (dyl:Win.Docs) and adds what each one opens (Dyl:DocsPage, Dyl:DocsTarget: the website, in the language of DynALisp).
  2. Dyl:Window (Bridge.cs) reads the values into a Session and shows the window over AutoCAD, modal (Application.ShowModalWindow).
  3. Session.Load reads the file with the WPF reader (the dyl: prefix, clr-namespace:DynALisp.Windows with no assembly, is the plugin itself) and merges into its resources the styles of Theme.xaml and the Dyl.* brushes of the theme of AutoCAD (Theme.Brushes: the grey blue of its palettes in the dark theme, COLORTHEME 0, its light greys else, its blue for what is picked; a CheckBox is drawn as a switch, as in the settings of Windows 11); a dark window gets the dark title bar of Windows. Its root must be a Window; a file that does not read, or is missing, makes Dyl:Window return nil, the reason on the command line.
  4. View finds every control by its name (x:Name, the key), gives it its value, and puts its value back each time it changes; the rules are then checked again (Refresh).
  5. A button closes the window with its number, opens a sub-window over it on the same values (its Cancel puts them back), turns every checkbox on or off, or opens the docs. When the window closes, Dyl:Window returns (status (key . value) ...).

The Window File

A window file is plain XAML, with no code: a control is named by its key, and the dyl:Win.* properties (Engine\Win.cs) say what it does.

The Preview Of A Hatch

HatchTile draws a hatch from the line families of its pattern, read from its .pat file by Pat.Read (angle, origin, offset and dashes of each family; kept until the file is written again, so a pattern rebuilt by Dyl-RebuildPat is read again). It follows the Presets And Materials convention on previews: the hatch at its size on paper, 1:1 on the screen (a WPF unit is 1/96 in).

  • Its Spec, given by the Lisp, is one band or the bands of an assembly side by side, divided by *, the fields of a band by ?: P?width?pattern?file?ppu?angle?scale a hatch, F?width a solid fill, S?width a space, L?0 a line between two bands, X?width a hatch preset missing (crossed out, as a pattern no file defines).
  • ppu is the inches on paper of one unit of the pattern: the scale of the hatch preset (divided by 25.4 for a metric pattern), divided by the drawing scale scale unless the preset keeps its size on paper (Dyl:QuickDrawGalleryBand: annotative or adaptive scaling, so a Drafting hatch preset; scale is then 1). The drawing scale is Remote>>Dyl:MaterialDrawScale (CANNOSCALEVALUE).
  • When fewer than three repeats of a pattern (Pat.Repeat: the widest spacing between its lines; not its dash periods, since a stipple reads as a texture at any size) fit in the height of the tile, it zooms out to the next step of 1, 2, 2.5, 4, 5, 8, 10, 16, 20, 25, 40, 50, 100... that shows them, one zoom for every band of the tile, and writes 1: and scale times the zoom in its bottom right corner. A family whose lines would be closer than 0.8 unit, or a tile of more than 20000 segments, is drawn as a grey fill.
  • Every segment of a band is one StreamGeometry, frozen, drawn in one call: a gallery of 50 tiles draws in a few milliseconds. Its colors are the brushes of the theme (Ink, Fill, LabelBack: Dyl.Text, Dyl.Input, Dyl.Surface in the gallery).

Preset Windows

A window that lists presets and edits the one shown (Quick Draw so far) is a preset window: its list is a ListBox named lst, and the Lisp gives its presets as a table, pst/rows. The window is then run by PresetEditor (Engine\Presets.cs), which does in the window everything the preset dialog of the Lisp engine did with a call for each click: the list (filter, sort, Show group, Set default), the presets selected (a value changed is given to all of them), New, Copy, Delete, Reset Selected, Reset All (Delete and Reset All ask first), and the aliases of the command of the preset shown. Nothing calls the Lisp back: it gives the presets, gets them back as edited, checks them again and saves them.

  • Tables – a value given as a list of lists, ("pst/rows" ("qd-Brick" "Section" "Brick" ...) ...), is a table (Session.Rows); the tables the window changes come back the same way, after the values: (status (key . value) ... ("pst/rows" row ...) ("pst/als" ...)). In a sample of Shots, a line +pst/rows=qd-Brick<TAB>Section<TAB>Brick... adds a row.
  • The values – pst/tiles names the control of each column ("nam:2,grp:1,mth:4,hbr:28:inv": inv a checkbox showing the inverse of its column, up a text saved in capitals). When the preset shown changes, the editor fills them (quietly: no rule runs for each one), then the rules are checked once. A value changed is written in the column of every preset selected, its list item updated in place.
  • The rows – the columns of the presets file, then the columns the Lisp adds for the window only (the text beside an open button, the preview of an assembly), read only: the Lisp cuts them off before saving (Remote>>Dyl:PresetWinCut). The editor sets pst/solid to "1" when the hatch preset of the preset shown is SOLID, for the rules.
  • The aliases – pst/als, ((ALIAS COMMAND) ...), shown as chips (als). An alias is refused, with its reason in ams, when it has other characters than letters, digits, - and _, is the command itself, starts with DYL-, LM- or PST-, is an alias already, or is a name of pst/taken (the commands defined, the aliases of acad.pgp: Remote>>Dyl:PresetWinTaken). A custom preset without id gets cu-<Name> with its first alias, as Remote>>Dyl:PresetCamel.
  • The checks – each value is checked as it is typed (dyl:Win.Check, a unique and not empty name, a group, a hatch preset that exists): a value not valid is not kept, its message is shown in error, and the list and the buttons that close the window are refused until it is fixed (Cancel always closes).
  • The Lisp side – Remote>>Dyl:PresetWin (Remote\Dyl-Presets.lsp) shows the window of a preset tool whose spec has (window . "Dyl-QuickDraw.xaml"), gives it its values (Remote>>Dyl:PresetWinVals), reads them back (Remote>>Dyl:PresetWinGet), checks the presets changed with the check of the App and the new aliases with getcname (Remote>>Dyl:PresetWinCheck: the first one not valid opens the window again on its preset, its message shown), and runs the code of an open button (Remote>>Dyl:PresetDlgCode) before showing it again. A tool without window keeps the DCL dialog (Quick Shape, Hatch Presets).

Lists Of Rows

A window that edits a list of rows (the layers of an assembly, the groups of the presets) has a ListBox with dyl:Win.Rows="1". The window is then run by RowsEditor (Engine\Rows.cs): the rows are added, edited, removed and ordered in the window, with no call to the Lisp, which gives them, gets them back as edited and checks them again (Assembly Layers, Preset Groups).

  • The rows – for the list k: k/rows the rows (a table), k/new one row, what the fields show while the list is empty and the row Add starts from, k/defs the rows of Reset, k.sel the rows selected ("0 3"). It gives back k/rows and k.sel. The list shows RowItem: {Binding [n]} the text of column n (the label of its item when a field with a list shows it), {Binding V[n]} its value, for the DataTriggers of its ItemTemplate.
  • The fields – dyl:Win.Column="n": the control shows column n of the row shown (the first one selected): a ComboBox the value stored for its item (key/vals), a TextBox its text, a CheckBox "1" / "0". A field changed goes to every row selected that its rules hold for (the dyl:Win.EnabledBy of the field and of the panels holding it, read on that row), their other columns kept. dyl:Win.Unique="message": no two rows with the same text (any case), greyed out while several rows are selected, a row added gets (2). dyl:Win.Follows="lp/widths": the field takes the item of that list (one for each item of the field lp) when lp changes, if it was empty or the item of its former value.
  • The buttons – dyl:Win.Do: add (a row of the fields after the rows selected), remove, up, down (one row selected), flip (the rows the other way), reset (k/defs), each one greyed out when it can do nothing.
  • The summary – dyl:Win.Summary on a TextBlock or a GroupBox (its header): {count}, {count:lk=L|line|lines} (the rows a rule holds for, a rule without |, with their noun), {sum:2:lk!=L} (the total of a column), {sel| (# selected)} (shown when two or more are selected); dyl:Win.SummaryEmpty while the list is empty.
  • The checks – a field is checked as it is typed (dyl:Win.Check, dyl:Win.Unique): a value not valid is not kept. On OK, every row is checked for every field its rules hold for, the first one not valid selected with its message; dyl:Win.Check="rows" on the list keeps one row at least.

The window runs alone while it is open: nothing calls the Lisp back. A button that must run Lisp (a command, a window not moved yet) closes it with its number, and the caller opens it again on the values it got: c:Dyl-Settings does so for the open buttons of Auto-phase (4), Auto draw order (5), System variables (6), Auto layer keys (7) and Revisions (8).

Moving A DCL Window

  1. Write its .xaml in the same Res folder, one file per dialog, its controls named by the keys of the DCL tiles, so the Lisp keeps its names. What the actions only greyed out or turned off (mode_tile, Dyl:MoreTile) becomes a rule of the file; a sub-window opened by an action becomes a dyl:Win.Open file on the same values.
  2. In the Lisp, the set_tile / start_list of the fill become a function giving the values (Dyl:SetWinVals), the get_tile of the OK a function reading them back (Dyl:SetWinGet); load_dialog, new_dialog, action_tile and start_dialog become one Dyl:WinShow.
  3. Delete the .dcl and the DCL functions (no copy is kept: DynALisp needs AutoCAD 2015). Add a row and sample values for its picture to Shots.csv, and update its developer docs page.
  4. Try it in AutoCAD 2025 or later and in an older one (the .NET Framework DLL).

The Pictures Of The Docs

Installer\Windows\Shots draws each window of Shots.csv (the window file, its sample values in Samples\, the picture its docs page names) with the engine of the plugin, at twice its size, under a plain title bar, in the light theme and in the dark one (<Page>-window-dark.png, shown by the website in dark mode). It needs Windows (WPF): dotnet run -c Release in that folder, then commit the pictures. The Windows workflow runs it on each push that changes a window file or the plugin: on a work branch, it commits the pictures that changed to it (pull before pushing again); on main, they are only an artifact of the run.

Known Limitations

  • No callback to the Lisp while a window is open (see above).
  • The theme is read when a window opens (COLORTHEME: 0 dark, 1 light): a window open while the theme changes keeps its own.
  • The windows are in English, as the DCL windows were.
  • 64-bit only: a 32-bit AutoCAD (2015 to 2019 had one) does not load the plugin.
