Versions And Updates

Developer docs – Conventions · Dynalisp Module – Developer docs · Making A Module · User Guide

The Versions And Updates conventions of DynALisp, part of the DynALisp Conventions: read before changing the version, a release, the setup or the uninstall, or a .NET plugin. When a new convention of this topic is agreed, add it here, with the reason for it.

  • The version of DynALisp is the AppVersion of PackageContents.xml, and only there: Dyl-Info, the setup and the release all read it. Its ProductCode never changes.
  • Each version has its section at the top of CHANGELOG.md: a ## <version> - <date> heading, then one short line per change (plain ASCII: AutoCAD reads the file as is). Raise AppVersion and add its section in the same change.
  • A release is a v<version> tag pushed to the source repository (DynALisp.bundle, private): the release workflow builds the setup (Installer\Build.ps1) and publishes the release to the public releases repository (DynALisp.release, *dyl:relrepo*), with the setup and CHANGELOG.md as files and its changelog section as notes. Users, the setup and Dyl-Info only ever link to the releases repository; only git clones use the source one.
  • 1.x and 2.0: DynALisp 2.0 and later run in AutoCAD 2025 and later only (every component of PackageContents.xml has SeriesMin="R25.0" or later, the setup refuses a computer without such an AutoCAD); 1.x, the last version for AutoCAD 2015 to 2024, lives on the branch release/1.x (made from main on 2026-11-25), which gets fixes only, released as v1.<n> tags of that branch. 1.x offers an AutoCAD older than 2025 the newest 1.x release only (Dyl:InfoLatestOf of Dyl-Info), never a version it cannot run. A fix that both need is made on main and copied to release/1.x (git cherry-pick), never the other way: main is the version that goes on.
  • DynALisp is installed with the setup or as a git clone. The setup installs only the files git knows (never User, MyTools, the dev files or the Docs and DevDocs folders of the modules, which open on the docs website), removes the shipped folders before copying the new ones, waits for AutoCAD to close, and never installs over a git clone. A git clone is updated with git pull.
  • The uninstall is clean: it offers to save the settings first (see User Files), then removes the whole folder and everything DynALisp added outside it (the Dynalisp* user settings, the DynALisp profile, the paths into the folder in the AutoCAD profiles). Anything new that DynALisp adds outside its folder must be removed by the uninstall too (CleanProduct in Installer\DynALisp.iss).
  • A .NET plugin (the clean startup, Installer\Startup; the windows, Installer\Windows...) is one project built twice and committed: for .NET 8 with the references of AutoCAD 2025 (Contents\Resources\<Name>.dll, AutoCAD 2025 and 2026, SeriesMin="R25.0" SeriesMax="R25.1") and for .NET 10 with the references of AutoCAD 2027 (Contents\Resources\Net10\<Name>.dll, AutoCAD 2027 and later, SeriesMin="R26.0"), a component of PackageContents.xml each. AutoCAD 2027 is not binary compatible with 2025 and 2026, so one DLL never serves both. Its code is the same in both builds, without #if (both are .NET), and the .NET 10 SDK builds both. It defines a Lisp function the Lisp side checks before using it ((if Dyl:CleanStartup ...)), and a window greys out what it does when it is not loaded. A plugin that reaches into AutoCAD itself by reflection (the lines of the command line) does nothing when it does not find what it looks for. A plugin never relies on a Lisp call made while DynALisp loads: it reads the Dynalisp* settings it needs itself when it starts (FixedProfile\General of UserRegistryProductRootKey, as DynALisp.Startup.dll and Translations.cs do), and asks the Lisp side for the state of the drawing when AutoCAD is idle. Every class that holds a LispFunction or a CommandMethod is listed in an [assembly: CommandClass(...)] of the plugin: AutoCAD registers the methods of those classes only (a static class cannot be listed), and a Lisp function it never registered makes every (if Dyl:X ...) of the Lisp side do nothing, with no error.
  • A calculation that needs no AutoCAD (the simulation of a 2D detail, the reading of the data files of the core) is a library of its own with no reference to AutoCAD (Installer\Simulation\Core, Installer\Core\Data), compiled into its plugin (the plugin stays one DLL) and tested alone (dotnet test Installer\Simulation\Tests, dotnet test Installer\Core\Tests) by a workflow on each push that changes it (.github/workflows/simulation.yml, core.yml). A plugin builds on Linux too (-p:EnableWindowsTargeting=true, the .NET 10 SDK of Microsoft: the one of Ubuntu has no WPF, which a plugin without WPF does not need), so its DLLs can be built and committed from any computer.
  • The core of DynALisp in .NET (Installer\Core, DynALisp.Core.dll, plan B) takes over, one step at a time, what Lisp does slowly in each drawing, never all at once: its first step reads the data files once per session (Dyl:Data, see User Files). A function of the core gives exactly what the Lisp code it replaces gives, so the Lisp side calls it when it is defined and keeps its own code for when it is not (Remote>>Dyl:CsvReadLisp), tested by the tests of its library on the data files of DynALisp themselves; its component is listed first in PackageContents.xml, so it is loaded before the first drawing.
  • What the C# of the core does as the Lisp does (the presets, groups, aliases and assemblies of Installer\Core\Data, with the distof and rtos they need) is checked against witness files taken in AutoCAD, never against what the Lisp is thought to do: Installer\Core\Tests\Witness\Witness.lsp (run by Pst-DiagnosticsWitness) runs the Lisp on the test cases of Witness\In (each a Contents and a User folder of its own, the Lisp pointed at its copy for a moment, the core hidden) and writes what it gives; its files, put in Witness\Lisp, are compared by WitnessTests.cs, line for line and each file written byte for byte. A step that moves more Lisp to the core adds its cases and its steps to both, and the witness is taken again.
  • The Manager moves to the core tab by tab (plan B): one window of DynALisp.Windows.dll, which reads and writes its data through DynALisp.Core.dll (one store of the data for the session). A tab moved to .NET has its Lisp window code removed, not kept for when the DLL is not loaded (the windows need DynALisp.Windows.dll anyway); what draws in the drawing stays in Lisp.
  • A file edited by DynALisp at run time never goes under Contents (see User Files): an update replaces the shipped folders whole.

Why: AutoCAD 2025 and later run .NET 8 and .NET 10 only, so one kind of build serves them all and the code has no case for older versions, while the users of an older AutoCAD keep a version that works and its fixes; one version number for every reader, updates readable without a GitHub account while the source stays private, users told what changed on each update, the users' edits kept by every update, and nothing left behind by the uninstall unless the user saves it.; a calculation tested apart is checked on every push, without AutoCAD; the core grows by steps that each keep DynALisp working with or without its DLL, so each one is tried in AutoCAD alone and nothing is rewritten at once; the container the code is written in has no AutoCAD, so what the Lisp really gives is taken where it runs, once, and checked on every push after; a window that cannot open without its DLL gains nothing from a Lisp copy of itself, which would only have to be kept the same
